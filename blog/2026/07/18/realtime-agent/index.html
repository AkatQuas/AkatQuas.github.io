Realtime Agent 调研：流式交互与桌面语音链路

July 18, 2026 · 12 min read

Realtime Agent 要的是边听边想边说、可打断、低时延。下面整理能力定义、与现有 Agent Loop 的平行接入，以及桌面端双向语音通话的分层参考。

核心定义​

普通传统 Agent：一问一答、单次轮次、等待完整输入才开始思考输出，用户说完一整段话才回复，有明显延迟。

Realtime Agent（实时 Agent）：流式、边听 / 边读、边思考、边输出，全程低延迟，支持中途打断、实时感知上下文变化，和人实时对话几乎无割裂，核心关键词：低时延、流式交互、中断响应、实时状态感知。

Realtime 的核心功能​

  1. 流式输入输出 文本 / 语音边输入边解析，AI 边思考边分段返回，消除等待空白； ← 依赖 real-time 的模型，例如 gpt-4o-realtime-mini 
  2. 支持实时打断 用户中途修改指令、打断 AI 输出，Agent 立刻终止当前推理，切换新需求；
  3. 实时动态工具调用 不用等完整提问，识别到半句话里需要工具，就实时调用工作流 / 接口；
  4. 实时状态同步 实时展示 Agent 当前步骤：正在理解、正在拉取数据、正在编排动态 workflow、正在逼近目标；

基于现有 Agent Loop​

不能重做一套独立框架，要做成平行模式：

  • 原有普通轮询 Agent、goal 目标 Agent、dynamic 动态工作流、realtime 实时 Agent 四种模式共存；
  • 复用统一的工具调用、记忆存储、任务调度、上下文管理底层能力；
  • Realtime 只是上层交互通道改造，核心任务执行逻辑复用现有代码，降低改造成本、方便迭代滚雪球。

和另外两个模块联动​

  • Realtime + goal 模式：实时同步目标进度，中途改目标自动重新拆解步骤；
  • Realtime + dynamic-workflow：用户实时变更需求，动态刷新任务链路，不用重新发起会话。

开源方案​

OpenAI Realtime API 完整链路：音频 / 文本实时流、会话状态管理、实时 Function Calling、中断机制；

  • https://github.com/openai/openai-node/blob/HEAD/realtime.md

核心能力：

  1. 原生融合标准 Agent Loop，普通 Agent/RealtimeAgent 平行共存
  2. 内置实时打断、流式工具调用、多 Agent 会话交接、长上下文增量更新
  3. 同时支持文本实时流 + OpenAI Realtime 语音音频流双模式
  4. 工具、记忆、路由、防护护栏完全复用普通 Agent 底层逻辑
  • https://openai.github.io/openai-agents-js/guides/voice-agents/quickstart/

基于 @openai/agents 库，使用real-time能力，创建一个 语音Agent。

一个语音 Agent 需要的能力包括添加工具、交接和护栏。

支持 轮次检测和语音活动检测、打断以及手动响应控制，控制对话循环。

支持添加文本输入、图像输入和会话历史管理。

  • https://github.com/openai/openai-realtime-agents

官方多实时 Agent 编排 Demo ，Next.js 完整前端 + 后端参考实现，展示两大生产范式

  1. Sequential Handoff 顺序交接：实时会话自动切换 goal 任务 Agent
  2. Chat-Supervisor 主管调度：单实时会话动态调度 dynamic-workflow 子流程

开源 Realtime Agent 标准范式（架构设计）​

范式 1：外挂并行实时层范式（OpenAI Agents SDK，推荐你们采用）​

  1. 底层统一：原有 Agent Loop、动态工作流、Goal 规划完全不动
  2. 上层包装：新增 RealtimeWrapper/RealtimeAgent 包装器，做长连接 / 流 / 打断处理
  3. 运行模式：同一套系统可切换「普通轮询」/「实时流式」双模式，代码复用 90%+

范式 2：事件驱动状态机实时循环（Pipecat / LiveKit）​

  • 核心：会话拆分为 Listening→Thinking→Speaking→Interrupted 状态机
  • 用户每输入片段触发一次增量推理，中途打断直接重置状态，终止当前 LLM 生成
  • 适合强交互语音场景

范式 3：流式 Graph 分支循环（LangGraph Realtime）​

  • 在 Agent 有向图中增加实时流并行分支，同步执行任务规划 + 实时交互输出
  • Goal 目标变更、动态工作流更新实时同步到流式输出

范式 4：多 Agent 实时会话交接范式（OpenAI Realtime Agents Demo）​

  • 单个长连接会话内部，根据用户实时意图自动切换不同专用 Agent（目标 Agent / 动态工作流 Agent）
  • 无需重建 WebSocket，上下文无缝继承

豆包桌面端 real-time 模式体验​

  1. 开启 realtime 模式，等同于增加一个 channel 输入来源，为 audio 输入。
  2. 对话输出含文本（先进会话记录）与语音推流；文字通常更快，语音可中断停止播放。
  3. 历史回溯主要是文本：用户 ASR 文本 + 助手回复文本；语音本身不进历史、无需回放。
  4. UI 随语音输入模式变化（波形、状态等）。
  5. 多模态：文字历史 + 当次语音输入一起送模型。
  6. 停顿会导致 ASR 中断或变更，用户 prompt 可能随之变化。

豆包 / 讯飞星火 / 通义千问 / 智谱清言 / Kimi 桌面端都试过：当时只有豆包支持双向语音通话，其余多为语音转文字。

豆包桌面端语音通话：Electron 分层与时序​

前置基础架构​

豆包桌面端基于 Electron = Node.js 主进程 + Chromium 渲染进程，语音通话依赖：

  1. WebRTC：麦克风实时采集、本地音频流
  2. 流式 ASR + TTS：云端识别与合成、本地播放

分层结构（三层）：

  1. 主进程（Main，Node.js） 系统硬件权限管理者：麦克风、扬声器、全局权限、网络长连接、IPC中转； 控制音频设备抢占、降噪、多音色调度、后台播放。
  2. 渲染进程（Renderer，Chromium Web） UI交互层：通话界面、按钮、波形动画、音色选择、状态展示； 通过 WebRTC 获取原始音频流，推送至主进程转发云端。
  3. 云端语音服务集群 ASR实时语音识别、大模型对话推理、TTS流式语音合成、音频编解码。

分层职责简表​

层级核心语音相关职责
Electron 主进程麦克风权限校验、音频设备管理、WebSocket长连接、音频流转发、TTS音频播放、异常兜底断连
Chromium渲染进程WebRTC采集麦克风PCM音频、UI交互（按住说话/免提切换）、波形渲染、通话状态展示
云端语音服务实时流式ASR转文字、LLM连续对话推理、流式TTS音频分片下发、降噪算法

二、完整语音通话交互流程（两种模式：按住说话 / 免提连续对话）​

交互逻辑简述​

  1. 用户左侧「更多」打开语音通话，独立弹窗启动；
  2. 首次触发请求麦克风权限，主进程拦截权限申请并持久化授权；
  3. 两种交互模式：
    • 按住说话：长按麦克风按钮才采集音频，松开终止上传；
    • 免提连续对话：持续拾音，VAD人声检测自动切分语句，无需手动按键；
  4. 本地音频实时分片上传云端 ASR，边说边转文字；
  5. ASR文本实时送入大模型流式推理；
  6. LLM输出文字同步送入TTS，分段下发合成音频流；
  7. 客户端边接收TTS音频边播放，支持打断（用户说话立刻终止当前AI语音）；
  8. 支持切换音色、实时波形可视化、通话中断恢复、后台播报。

三、Mermaid 时序图：完整语音通话链路时序​

sequenceDiagram
    participant User as 用户
    participant Render as Chromium渲染进程(UI/WebRTC)
    participant Main as Electron主进程(Node)
    participant Cloud as 云端语音&大模型服务

    Note over User,Cloud: 阶段1：初始化通话、授权麦克风
    User->>Render: 点击「语音通话」打开通话窗口
    Render->>Main: IPC请求麦克风权限 + 建立语音WebSocket长连接
    Main->>OS: 请求麦克风硬件权限
    OS-->>Main: 返回授权结果
    Main-->>Render: IPC推送权限成功/失败
    Render->>Render: 初始化WebRTC AudioContext，准备音频采集

    Note over User,Cloud: 阶段2：用户持续说话（免提VAD/按住说话）
    loop 实时音频分片采集上传
        User->>Render: 持续人声输入麦克风
        Render->>Render: WebRTC采集PCM原始音频帧，做本地降噪
        Render->>Main: IPC转发音频分片二进制流
        Main->>Cloud: WebSocket流式上传音频包
        Cloud->>Cloud: ASR实时识别，输出增量文本
        Cloud-->>Main: 下发实时转文字结果
        Main-->>Render: IPC回传识别文本，UI展示实时字幕
    end

    Note over User,Cloud: 阶段3：云端推理+流式TTS返回语音
    Cloud->>Cloud: ASR完整句子送入LLM流式生成回复文本
    loop TTS流式分片下发
        Cloud->>Cloud: 分段生成TTS音频二进制片段
        Cloud-->>Main: WebSocket下发合成音频流
        Main->>Main: 音频缓冲、扬声器调度
        Main-->>Render: 同步推送AI回复文字用于UI展示
        Main->>OS: 扬声器播放TTS音频
    end

    Note over User,Cloud: 阶段4：打断机制（用户再次说话）
    User->>Render: 用户重新开口说话
    Render->>Main: IPC发送「打断指令」
    Main->>Cloud: 发送终止当前TTS会话信号
    Main->>OS: 立刻停止扬声器播放AI语音
    Note over Main,Cloud: 回到阶段2，重新采集用户音频循环

    Note over User,Cloud: 阶段5：关闭通话
    User->>Render: 关闭语音通话窗口
    Render->>Main: IPC发送关闭会话指令
    Main->>Cloud: WebSocket关闭语音连接
    Main->>OS: 释放麦克风硬件占用
    Render->>Render: 销毁WebRTC音频上下文，清空通话UI

四、关键架构设计亮点（针对语音通话场景）​

1. 主进程统一接管硬件，解决 Chromium 内核碎片化问题​

纯网页端WebRTC会受浏览器、系统版本限制，Electron主进程统一封装麦克风/扬声器：

  • 避免多软件抢占麦克风冲突；
  • Windows/macOS 音频设备差异由Node层统一兼容，渲染层只处理标准音频流；
  • 后台通话播报、最小化窗口持续收音依赖主进程后台常驻能力。

2. IPC 分层解耦，安全隔离​

  • 渲染进程（网页沙箱）只负责采集音频、UI展示，不直接操作硬件、不直连云端WebSocket；
  • 所有网络、硬件操作收敛到主进程，防止前端JS漏洞劫持音频流；
  • 音频二进制流通过IPC中转，统一加解密、校验。

3. 流式双向链路，低延迟核心设计​

  1. 上行（用户→云端）：音频分片 20–40ms 小包上传，ASR边收边识别，实现“边说边出字”；
  2. 下行（云端→用户）：LLM 输出一段文字立刻触发一段TTS合成，分段下发音频，不用等完整回答再播放；
  3. 打断机制：用户人声检测触发指令，立刻切断TTS播放，做到自然对话感。

4. WebRTC 本地音频预处理放在渲染层复用网页能力​

网页端早已成熟的音频降噪、音量波形计算、VAD人声检测全部复用，不用在主进程用C++重写音频算法，大幅降低开发成本。

5. 与普通文字播报的区别​

普通“消息语音朗读”是一次性拉取完整文本合成； 语音通话模式是长连接流式实时双向音频流，独立WebSocket通道，优先级高于普通对话消息，单独做音频缓冲、人声打断、硬件独占逻辑。

五、极简交互总结​

  1. 用户打开语音通话窗口 → 主进程申请麦克风、建立专属语音长连接；
  2. WebRTC采集人声，分片经IPC传给主进程上传云端ASR；
  3. 云端实时转文字+大模型推理+流式TTS；
  4. TTS音频流回传客户端，主进程控制扬声器播放；
  5. 用户新说话自动打断AI语音，循环往复；
  6. 关闭窗口释放麦克风、断开语音连接。
