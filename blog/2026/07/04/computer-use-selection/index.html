Computer Use 选型札记：从 Codex 复刻到 Node 生态

July 4, 2026 · 8 min read

从 Codex 桌面 Computer Use 的 AX 树机制出发，对照开源边界与 Node 生态选型，方便给 Agent CLI 加「手和眼」。

一、起点：Codex 的 Computer Use 到底是什么​

Codex 桌面 App 的 Computer Use 能力，核心机制是 “无障碍树（AX Tree）驱动 + 元素引用寻址”，而非纯视觉坐标点击。

  • 模型看到的状态：不是一张截图，而是带索引的结构化元素列表。底层通过 macOS 的 AXUIElement API 获取按钮、输入框等节点，为每个可交互元素分配 element_index。
  • 模型输出的动作：类似 click(app="com.apple.stocks", element_index="12")，而非 click(x, y)。执行层再把索引解析成真实系统原生元素 ID 去触发。
  • 截图只是辅助：用于“视觉 grounding”，不是主要定位手段。

这个设计的关键优势在于稳定性：结构化元素引用比像素坐标抗分辨率变化、抗窗口位移的能力强得多。

二、开源边界：CLI 与桌面 App 的能力隔离​

openai/codex 开源仓库不具备桌面操控能力。

  • 开源的是 CLI：定位为终端里的编码代理，核心能力围绕读写文件、执行 Shell、管理 Git 等软件工程任务。没有截图、鼠标控制、键盘模拟或 UI 元素识别接口。
  • 闭源的是桌面 App 的 Computer Use 插件：通过 openai-bundled 插件提供，运行时依赖一个名为 SkyComputerUseService 的本地原生辅助程序（macOS 上是 Codex Computer Use.app），负责截图、AX 树读取、模拟输入。这个辅助程序及其通信协议都是闭源的。
  • CLI 要使用该能力：需要桌面 App 已安装并运行，能力来自桌面 App 而非 CLI 本身。

社区已有逆向分析（如 open-codex-computer-use 项目）摸清了部分实现细节，包括光标运动算法参数、JSON-RPC 通信协议等，但逆向出的主要是表现层逻辑，底层的权限管控、安全沙箱和系统级输入注入机制仍是难以复刻的壁垒。

三、平台差异：macOS 原生 vs Windows 前台接管​

Codex 桌面端是双端原生的，但两端的“原生”程度不同。

macOS 版：系统级原生集成​

  • 依赖 ScreenCaptureKit 和 AVFoundation 等苹果专用框架。
  • 通过 Apple 授权插件实现锁屏后台操作，任务期间临时解锁但保持屏幕遮盖。
  • 能在看不见的虚拟屏幕上操作，不占用用户当前的鼠标键盘。

Windows 版：跨平台框架上的适配版本​

  • 外壳是 Electron 应用（逆向确认运行在 Electron 42 上），核心是 Rust 工作区。
  • 没有对等的系统级虚拟显示或授权机制，因此只能前台接管当前桌面会话。
  • 已知问题包括：高 DPI 缩放下的坐标精度 Bug、运行时桥接不稳定、对 UAC 弹窗无力、缺少锁屏操作能力。
  • 体验上需要用户“交出电脑”，任务期间基本干不了别的。

四、Node 生态选型：跨平台方案对比​

在 Node.js 生态中复刻 Codex 方案，核心要求是 跨平台 + 无障碍树驱动 + 生态活跃。

首选：@simular-ai/simulang-js​

  • 能力全面：键鼠模拟、截图、剪贴板、无障碍树检查等原语。
  • 跨平台覆盖最全：预编译二进制覆盖 macOS (arm64/x64)、Windows (x64/arm64)、Linux (x64/arm64)。
  • 纯 Node 集成：直接 npm install，不需要 Python 或额外进程，提供统一的 Machine.local() API。
  • 定位匹配：设计目的就是嵌入到自己的 Node 应用里使用。

备选：mechatron​

  • 支持 Linux (x64/arm64)、macOS (arm64/x64)、Windows (x64/ia32)。
  • 基于 napi-rs 的 Rust 原生模块，纯 Node 集成。
  • 老牌库 robot-js 的现代重写版，API 兼容，社区有一定积累。
  • 更偏向传统键鼠模拟，对无障碍树的需求支持不如 simulang-js 直接。

平台限制提醒​

  • @simular/simulib-js 和 @nuvin/computer-use 都要求 macOS 14+，原因是它们依赖 macOS 14 才开始稳定/可用的无障碍 API 特性。
  • @nuvin/computer-use 需要从源码构建 Swift helper，Windows 侧的无障碍树（UIA）在 Node.js 生态里封装相对零散。
  • 注意 npm 上的 scope 迁移：@simular/simulib-js 是正确活跃的包，@simular-ai/simulib-js 是旧版 scope 或占位，不应使用。

五、特殊场景：CEF/Electron 的无障碍盲区​

CEF（Chromium Embedded Framework）和 Electron 这类应用的无障碍树往往很“浅”——系统 API 通常只能看到窗口边框、菜单等外壳元素，看不到内部网页渲染出的按钮、输入框，因为那些内容由 Chromium 自己的渲染引擎管理。

解决方案：级联融合（Cascade）​

naturo 的核心优势就是用级联机制专门解决这个盲区：

  • 以 UIA（Windows）或 AXAPI（macOS）为基础树，动态叠加 CDP（Chrome DevTools Protocol） 来穿透 CEF/Electron 的渲染层。
  • 官方基准测试显示，在 VS Code（Electron）上，UIA-only 只能识别 13 个元素，级联模式能识别 111 个；CEF 场景也有从 55 个提升到 59 个的实测数据。
  • 与 CEF 配合时，确保启动参数中有 --remote-debugging-port，且该参数在调试模式和生产模式都要传递（有项目曾因只在 cfg!(debug_assertions) 下开启 CDP 端口，导致发布构建后自动化完全失效）。

六、集成到 Agent Coding CLI：以 pi 为例​

如果目标是给 pi-coding-agent 这类 Node Agent CLI 加上 Computer Use 能力，pi 本身已有现成的扩展生态，不需要从零“加”。

首选：pi 原生 computer use 扩展​

pi-computer-use（ishandotsh / injaneity 版本）机制与 Codex 最同源：

  • 在 macOS 上优先操作 Accessibility 目标（如 @e1），仅在 AX 覆盖不足时才回退到截图。
  • 支持 strict AX mode，可以在不抢占前台焦点、不接管鼠标光标的情况下操作。
  • 平台现状：macOS 是主力，Linux/X11 是坐标模式 MVP，Windows 暂未支持。

备选：Anthropic 原生 computer use 扩展​

pi-anthropic-computer-use 适合主要用 Claude 模型的场景：

  • 注册名为 computer 的工具，支持 16 种动作（screenshot、click、type、scroll 等）。
  • 自动改写 Anthropic API payload，注入 computer_20250124 工具类型和 beta 头。
  • 平台支持：macOS（依赖 cliclick）和 Linux（依赖 xdotool/scrot）可用，Windows 明确不支持。

底层库方案：自己封装​

如果不满足于现成扩展，用 @simular-ai/simulang-js 作为底层“手和眼”，自己写一个 pi 扩展来封装它的 AX 树读取和输入能力，是兼顾跨平台（含 Windows）的最务实路径。

七、选型决策速查​

场景推荐方案关键理由
最快用上、体验最好（macOS）pi-computer-use与 Codex 同源的 AX 引用机制，不抢占焦点
需要跨平台（含 Windows）@simular-ai/simulang-js 自封装预编译二进制覆盖三平台，纯 Node 集成
主要跑 Claude、用官方工具格式pi-anthropic-computer-use开箱即用，但 Windows 不支持
目标应用是 CEF/Electronnaturo + CDP 级联穿透渲染层盲区，元素识别率大幅提升
传统键鼠模拟为主mechatron平台覆盖广，robot-js 现代重写版

八、核心结论​

  1. Codex 方案的精髓是 AX 树 + 元素引用，不是截图加视觉坐标。复刻时应优先保证结构化元素寻址能力。
  2. 开源的是 CLI，闭源的是桌面操控。想直接用 Codex 的 Computer Use，需要桌面 App 在场。
  3. macOS 的体验优势来自系统级虚拟显示和授权机制，Windows 版是跨平台框架上的适配版本，短期内难以追平。
  4. Node 生态里 @simular-ai/simulang-js 是跨平台首选底层库，但如果你在 macOS 上用 pi，现成的 pi-computer-use 扩展更省事。
  5. CEF/Electron 场景必须叠加 CDP 级联，纯 AX 树看不到内部网页元素。
  6. 选型没有万能解：跨平台、生态活跃、纯 Node、AX 驱动这四个条件同时满足的方案极少，需要根据目标平台和开发语言做取舍。
