Kong 与原生 Nginx Ingress 架构对比

May 2, 2026 · 2 min read

Ingress 只是路由配置；真正听流量的是 Ingress Controller。一句话：Ingress 是图纸，Controller 是施工工人。

两种流量走向​

原生 Nginx Ingress​

外网请求
  → Nginx Ingress Pod（唯一入口）
  → 读取 Ingress 配置 + Service 列表
  → 经 kube-proxy 转发
  → 业务 Pod

特点：Nginx 既是入口又是控制器；后端依赖 Service，必须走 kube-proxy。

Kong Gateway​

外网请求
  → Kong Gateway Pod
  → 后台 KIC 监听 Ingress / Service / Endpoints
  → Kong 生成路由与上游节点池
  → 直连业务 Pod（绕过 kube-proxy）

特点：Kong 本身就是 Ingress Controller；Ingress 只当配置文件；直连 Pod 真实 IP。

核心差异​

维度Nginx IngressKong
服务发现Endpoints + ClusterIP，依赖 kube-proxyKIC 拉 Pod IP 进 Upstream，自带健康检查
控制面 / 数据面合一，改配置偏重 ReloadKIC + Gateway 分离，动态更新更轻
单 Pod QPS（经验区间）约 3k–5k约 8k–15k
长连接支持但配置麻烦WebSocket 等原生友好
插件很少JWT / 限流 / 熔断 / 灰度 / 日志

选型结论​

  • Nginx Ingress：简单官方轻量，适合纯 HTTP 转发、无复杂网关需求。
  • Kong：专业 API 网关，适合微服务、高并发、长连接（含 AI 会话 WebSocket）、要插件能力的场景。

对我们这类「AI 会话 + WebSocket + 多微服务」的业务，更倾向 Kong，把原生 Nginx Ingress 留给更简单的静态路由。
