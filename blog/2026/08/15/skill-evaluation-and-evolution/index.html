Skill 评价与进化：业界评测框架与 WingsApp 运行-评价-优化

August 15, 2026 · 5 min read

一边看业界 Agent Skill 评测工具怎么分层，一边落 WingsApp（办公智能助理桌面客户端）里「创作期评测 → 运营期质量报告驱动」的进化闭环。两条线拼在一起，才说得清「设计得好不好」和「线上要不要改一个字」。

一、业界 Skill Evaluation 速览​

横向看几家开源评测 / 安全扫描方案（维度是静态安全、去重、Agent 真实性、用例格式、baseline、企业/CI）：

维度SkillEvaluatorskilljack-evalsskilletnakiros
静态安全强（SkillSpector）弱无audit 分离
去重Tier 2无无无
Agent 真实性Harbor 沙箱 + 多 CLI多 runner，偏 host自研 loopClaude Code only
用例格式evals/evals.jsontask.md 包evals.jsonevals/evals.json
baselineHarbor 数据集默认 no-skill无（比 provider）with/without_skill
企业/CISARIF、Verified SkillsGitHub Actionmanifest + workflow本地 daemon

要点摘录：

  • NVIDIA SkillEvaluator：把「静态质量/安全」「语义去重」「真实 Agent 行为」拆成三个 Tier；Tier 3 用 Harbor 沙箱跑测，是层级最全的一条龙。
  • skillguard：纯本地、离线静态扫描，标准库 + 规则，无云端、无 LLM 调用。
  • snyk/agent-scan：本机发现配置后，深度分析走云端，需 Token。
  • nakiros：Audit（文档/最佳实践 lint）与 Eval（真跑 Agent + 断言）两条线；断言优先 script，语义才上 LLM。
  • skillet：多 Provider 真 Agent Loop，偏「哪个模型更适合这个 skill」，不是 Skill Lift。
  • skilljack-evals：真实 CLI/SDK trial + 确定性 verifier，默认同 no-skill 算 Lift，兼顾 TDD 内循环与 CI。
  • 另有 agent-skills-eval、skills-security（轻量版 skillguard）、以及 agentskills.io 对 evals.json 的约定。

云端免部署的扫描（如部分 skills.sh / Gen Digital 链路）往往 不支持 Self-host，企业内网要谨慎。

共性：动态评估极度依赖 test cases；evals/evals.json + with/without skill 几乎成事实标准。

二、WingsApp 里的三条线如何汇合​

WingsApp 对用户创作 skill 的长期维护，经历过三次概念迭代：

阶段核心思路输入典型动作
skill-creator创作期主动评测人工 eval 集、断言、with/without改 SKILL.md / description / benchmark
Hermes Curator日历 + 用量管库use_count、stale_after_daysarchive；可选 LLM 合并
Evolution Loop质量报告驱动静态 + 运行时 +（规划中）eval 摘要单 skill：noop / patch / schedule_eval

转向：不再用「多久没用」当主判据，也不默认跨 skill 合并；读的是 SkillQualityReport，不是日历。

skill-creator：设计得好不好​

内置创作与评测 skill（wingsapp-default-skills/skill-creator/），人类主导：

  1. 触发准确率（description 是否该加载）
  2. 任务完成质量（with-skill vs baseline）
  3. 可重复 benchmark（pass_rate、耗时、token）

流水线概要：evals.json → 并行 with_skill / baseline → Grader 断言 → 聚合 benchmark → eval-viewer 反馈再改稿。评委角色含 Grader / Comparator / Analyzer。

与 Evolution Loop 的分工：skill-creator 重评测、重人工、创作/大改；Evolution Loop 轻量、后台、单 skill 小 patch。包内 evals/benchmark.json 与 curator 侧 eval-latest.json 是预留的 ingest 接口。

Hermes Curator：曾用、现退场的主线​

触发：空闲 + 间隔（非 cron）。Phase 1 确定性状态机（active → stale → archived）；Phase 2 可选 LLM consolidate。不变量：只动 curator-managed、永不硬删、pinned/cron 豁免、mutating 前 backup。

WingsApp 保留 ledger、backup、install-guard、contentRevision sync、idle 门控；移除 stale/archived 生命周期与 consolidate 合并主线。

Evolution Loop：线上要不要改一个字​

仅桌面 Node、仅 curatorManaged 用户 skill。

运行：加载登记 → 引用判定 → task-end 结构化摘要 → runtime-observations
评价：静态分析 + runtime rollup +（规划）eval → report-latest / compositeBand
优化：空闲调度 → decide → noop | patch | schedule_eval

决策直觉：healthy → noop；失败/降级且无 eval → 入队评测；静态 issue 或 runtime 降级 → LLM 只 patch 当前 SKILL.md；unknown 等观测。

明确不做：archive、merge、跨 skill batch。compositeBand 不对用户展示。quality 目录不同步，各机本地重建。

已知缺口：schedule_eval → skill-creator 未闭环；纯语音 realtime 路径缺 finalize；patch 后自动 re-eval 未接。

三、对照与结论​

业界评测框架skill-creatorHermes CuratorWingsApp Evolution
问题框架能力边界设计得好不好库该不该瘦身合并真实使用要不要改一字
输入evals / 沙箱 / 安全规则eval 集 + 人审日历 + 用量静态 + runtime +（未来）eval
范围单次评测流水线单 skill 创作期全库单 skill 后台

一句话：

  • 业界方案回答「评测体系怎么搭、安全/沙箱怎么分层」；
  • skill-creator 回答「设计得好不好」——benchmark + 人审；
  • Hermes 合并/归档哲学在本阶段刻意退场，平台能力（ledger/sync/guard）继续服役；
  • Evolution Loop 回答「线上要不要改」——吃真实流量信号，只改自己。

创作期用评测建基准，运营期用质量报告吃流量；开源评测栈（尤其 SkillEvaluator / Harbor / evals.json 约定）是 skill-creator 与未来 schedule_eval 接线时最值得对齐的外部参照。
